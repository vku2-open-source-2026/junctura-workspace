# Changelog

## Unreleased

- Add the offline-first `pack:install --dry-run` slice of issue #12 in `scripts/pack-install.mjs` (runnable as `npm --prefix server run pack:install`): the command validates the pack first with the shared `readPack()` preflight, then prints a byte-stable ordered JSON plan — Directory unit-type, sample-unit and role-group PUT steps with the exact verified shapes of the pinned Foundation contract excerpt (`putDirectoryUnitType`/`putDirectoryUnit`/`putDirectoryGroup`, unit ids checked against the pinned path-parameter pattern so one-character ids are invalid input, units ordered parents-first by tree depth, role groups derived from step/open bindings per unit type), followed by `bpmn.definition.load` steps labelled `planned` with `blockedBy: junctura-dxos#112` (Core pins no definition-deployment operation) and `ws_packs` schema-registration and pack-record steps labelled `planned` with `blockedBy: junctura-workspace#12` (the pinned Core data-schema endpoint exists; the ws_packs schema design is not supplied by this issue), with no invented HTTP method, path or body, and workflow ids outside the pinned Core `definitionKey` pattern `^[a-z][a-z0-9_]{2,63}$` rejected before planning (`PLAN_DEFINITION_KEY_INVALID`, because a real validateDefinition would refuse them — the old Health draft with hyphenated keys is such a case). The dry run makes no network request (proved by a poisoned-network test), changes nothing, preserves group/unit references, and separates unsupported execution (exit 3 without `--dry-run`) from invalid input (exit 1, PackError-shaped errors on stderr) and usage errors (exit 2). Real execution, upgrade, removal, partial-failure retry and the version-must-increase check are explicitly not implemented; documented in docs/PACK_FORMAT.md and covered by focused CLI tests.
- Specify the Workspace pack format v1 in docs/PACK_FORMAT.md with draft 2020-12 JSON Schemas in `schemas/`, synthetic Education and Health fixtures in `examples/packs/`, and a dev-only jsonschema contract check in `scripts/check-pack-schemas.py` wired into CI.
- Extract the shared UI package `@junctura/ui@0.1.0-rc` under `packages/ui/` from the pinned Junctura Health library: 21 components, design tokens, styles and fonts, with health-domain defaults removed so apps supply them via props (quick find keeps only the neutral `Tìm kiếm` placeholder). CI typechecks, tests, builds and packs the package before the app checks.
- Promote the pinned Junctura Health input revision to `53b0a4041e2c54c7582686e494fb48d143728a25` (Health PR #47, add Health pack and verify Workspace UI compatibility): every path the portal builds from (`ui/`, `contracts/`, `workflows/`, `demo/plan.mjs`, `seed/data/accounts.json`) is content-identical to the previous pin `a24c8eb3…`, so portal behavior is unchanged. CI adds `pack/` to the Health sparse checkout and runs a new `node scripts/check-health-pack.mjs` step that verifies the pin before anything else — the version file must name a nonempty full SHA and the pinned checkout must sit exactly at it (`git -C .junctura-health rev-parse HEAD`) — then reads the real Health pack through `server/packs.mjs` `readPack` and asserts the canonical pack id `health` and its two definition keys (`recordTypes` chuyen-tuyen, thanh-toan and the hyphen-free workflow process keys `chuyentuyen`, `thanhtoan` required by the DX-OS definition policy; the pack's own group and unit type lists are not pinned), and fails when the pin is empty or not a full SHA, the checkout HEAD does not match it, the pack is missing or malformed, or its keys drift. The checker is covered by focused tests in `server/tests/health-pack-pin.test.mjs` that hand the checkout HEAD in as a value, so `npm --prefix server test` stays independently runnable and the real pinned pack is asserted by the explicit CI step.
- Import the Junctura Health portal and backend while preserving the portal's commit history.
- Specify the planned Tier 3 Workspace API in docs/API.md with an OpenAPI 3.1 contract in `docs/contracts/workspace-api.openapi.json` (cases, tasks, files, notices, directory with delegated user identity, the directory-admin gate on ordinary staff, cursor pagination, idempotency with the unknown-outcome 503 same-key retry, the records collection allowlist and the records/outbox completion payload), 21 synthetic fixtures under `examples/api/`, and a dev-only jsonschema contract check in `scripts/check-api-contract.py` wired into CI, all matched against the pinned DX-OS checkout excerpt and its documented gaps.
- Resolve portal staff identity from the DX-OS Directory instead of the seed accounts: `server/staff.mjs` now calls the implemented `GET /v1/identity` (pinned Foundation contract, `getVerifiedIdentity`) with the caller's own user bearer — never the app-scoped SDK `identity()` and no admin Directory fallback — maps the verified unit to the portal facility, requires the configured `JUNCTURA_TENANT`, binds the token's nonempty verified `sub` to the response `subject` exactly (a mismatch is 403 and grants nothing), requires every `unitPaths` entry to pair the exact `/{tenant}/{unit}` path with an advertised unit id (a contradictory answer is malformed 503, no access), and fails closed when no known unit is verified (several units pass only with an explicit `?unit=` that the verified membership contains). Errors separate no-staff/wrong-tenant/401/403 from a malformed answer or an unavailable core (503), the board write keeps its privilege tightened to verified `so-y-te` members carrying the `/so-y-te/ban-tin` group, the backend no longer reads `seed/` at runtime and the server image stops copying it, and docs describe deployment plus synthetic membership provisioning through the DX-OS Directory API (the old Health demo enrolled at tenant root only). Covered by focused contract and route tests.
- Add CI for license metadata, Compose configuration, backend tests, and frontend type checking, tests and build.
- Add the local pack reader and preflight in `server/packs.mjs`: `readPack(packDir)` validates a pack with the published draft 2020-12 schemas (Ajv), parses BPMN namespace-aware and rejects DTDs/external references, proves file containment including symlinks before opening references, and enforces the documented cross-file checks (duplicate ids, dangling references, open/step scopes, unit tree with one root, BPMN process/userTask ids) returning `{ ok, pack | errors }` with stable error codes and paths. Covered by focused reader tests and documented in docs/PACK_FORMAT.md; the version upgrade check of `pack:install` is left to issue #12.
- Add contributing and security policies plus issue templates for tasks and bugs.
- Promote the Education pack in `examples/packs/education/` from a draft into the runnable pack: connected Flowable BPMN flows (start → userTask → exclusive gateway → end) with valid sequence flows, `flowable:candidateGroups` role bindings, reachable decision paths for every declared decision (reject ends at its own end event, request-info loops back to the receiving step), and per-task deadline documentation consistent with the manifest; keep every stable id except the process keys, the two schools and the one education office, and bump the pack version to 0.2.0. Add a focused pack-flow regression test in `server/tests/education-pack.test.mjs` and the pack README documenting the synthetic API seeding guide plus the demarcation with `pack:install` (issue #12) and real-stack acceptance (issue #27).
- Fix a DX-OS compatibility bug in the Education pack: the pinned Core policy `validateDefinition()` rejects hyphenated BPMN `process/@id` values, so compact the process keys to the intersection of the Workspace stableId schema (`[a-z][a-z0-9-]{0,62}`, no underscores) and the Core process-key pattern (`[a-z][a-z0-9_]{2,63}`, no hyphens): `workflows[].id` and the matching `process/@id` become `chuyentruong` and `capbansaohocba` — the definition keys `pack:install` (issue #12) loads into the engine, verified against the pinned `validateDefinition(includeTasks: true)`. Record-type ids, BPMN file names, step/task ids and forms are unchanged.
