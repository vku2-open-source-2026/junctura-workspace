- Add real pack install and inspection to `pack:install` (issue #12 install slice, `server/pack-lifecycle.mjs` + `scripts/pack-install.mjs`): without `--dry-run` the command validates the pack offline first, then executes on the configured DX-OS stack — verified direct tenant console-admin operator and enrolled backend application identities before any mutation, plus a narrow read-only preflight `GET /v1/directory/unit-types?limit=1` on the same operator credential enforcing the Core requirement that the operator is also enrolled as a Directory manager with `directory.write` (a management enrollment bound to the verified subject, issuer and client, separate from the console-admin role BPMN publication needs; Core source `infra/postgres/037-directory-management.sql`, `docs/CORE_API.md`) — a 403 there is preserved verbatim and reported with zero ws_packs/Directory/Flowable mutations, and the install continues with the checked operator credential for Directory/BPMN and the backend credential for app-owned records. Then the `ws_packs` collection schema is registered desired-state on the blank owner scope, and the exact version plus content hash (SHA-256 over canonical manifest/units/BPMN) is durably reserved `installing` by key before any Directory or Flowable effect, finalized to `available` only under the record's If-Match ETag after every effect commits. BPMN publication follows the independently verified DX-OS PR #113 contract (merged at `bb6233f86633a42e1e1e5f58812a53064e6cd9b0`): per-workflow idempotency keys derived deterministically from `tenant|packId|version|op|contentHash` so any rerun after an uncertain outcome reuses exactly the same keys and bodies (never a fresh key), pending/ambiguous outcomes retried under the same key, success replies required to carry a nonempty id, the exact requested definition key and a positive integer version before finalizing, `definition_invalid` reported with the reservation kept incomplete. Directory reads go through the pinned list contracts (paginated `GET /v1/directory/units`, exact unit id match — the per-unit route pins PUT only) and an existing unit of a different unit type is never repurposed. The `ws_packs` schema uses only Core's PostgreSQL-safe regex subset (no groups or alternation, unescaped hyphen last) and re-declares no version length bound, so every manifest-safe version including long prereleases is recorded (record keys hash above the pinned 128 characters); `--list` (also `npm --prefix server run pack:list`) reads complete and incomplete installs read-only, distinguishing a fresh/absent collection (empty listing) from inaccessible data (reported error), and refuses out-of-scope or unorderable records. Every selection/activation/retirement path of the earlier draft is deliberately removed (an independent review found a genuine unsafe cross-record selection/retirement race); transaction-backed selection and retire over the pinned `/v2/data:batch` are explicitly deferred to the next PR, documented in docs/PACK_FORMAT.md. Exit 3 now means refused-without-effect (missing lifecycle configuration); the offline dry-run plan and its byte-stable output are unchanged. Covered by `server/tests/pack-lifecycle.test.mjs` (16 tests against a stateful mock Core on the HTTP loopback driven by the exact pinned SDK, including resume, two-install ordering, same-version content refusal, precondition/idempotency wire behavior and fail-closed identities) alongside the unchanged offline planner tests.
- Add durable pack selection and safe retirement to the closing #12 lifecycle slice (`server/pack-lifecycle.mjs` + `scripts/pack-install.mjs`): `--select <pack-dir>` activates the exact installed version whose mounted assets the operator points at — only an `available` complete version may be selected, the mounted pack's content hash must equal the version's recorded hash (`VERSION_CONTENT_MISMATCH` otherwise), and re-selecting the active version is a no-write replay — while `--retire <pack-id> <version>` marks only that version's `ws_packs` record `retired`, refusing the active selection (`RETIRE_SELECTED`) and never deleting deployed BPMN definitions, Directory resources or prior app records needed by existing cases. State lives in one app-owned `ws_pack_selections` record at the stable key `active`, bootstrapped with an empty pointer by regular by-key creation (a racing creation cannot overwrite), always re-read with its current strong ETag (a same-key creation receipt is never current authority), and read by `--list` through a small unfiltered page so a read-only listing works on a fresh owner whose schema/index does not exist yet (`400 invalid_query` there on real Core) without registering anything; `--list` now reports the active `selection` and a per-version `selected` flag. Selection and retirement each commit one atomic pinned `POST /v2/data:batch` — selecting replaces the pointer and re-validates the target with a same-data replacement under the current per-record ETag, retiring pins the same observed pointer ETag and re-registers the current retired-capable `ws_packs` schema as the record-retaining migration before its first `retired` write — so a simultaneous select and retire cannot interleave and the loser rolls the whole batch back (412, definite). Idempotency keys are derived from the exact observed ETag pair (identical observation = identical request/body = receipt replay; a CLI rerun re-reads committed state, and a fresh key is never picked automatically); uncertain outcomes stop with `PENDING_NOT_SETTLED` and rerun the same command, with the single `active` pointer as the self-evident commit marker. `docs/PACK_FORMAT.md` documents the commands, the batch semantics and the tested `JUNCTURA_PACK_DIR` relationship for mounting versioned pack assets in the portal deployment. Covered by focused loopback tests of the pinned wire contract (bootstrap receipt replay, stale ETags, both select-vs-retire orderings, schema migration, denials, resource retention, CLI).
